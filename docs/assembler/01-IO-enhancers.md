# 01-IO-ENHANCERS — Enhancers, re-derived - the door where you set your own price, and the two kinds it cannot express
> Source: `docs/Actual HTMLs Of designers/enhancersderived.html` · Component-designer door · Census (Phase 1 draft, unverified)

## What this door builds
This designer builds **enhancers** — small components that make some *other* thing better: a veteran cadre that lifts a warship's combat rating, power armour that lets a soldier carry a heavier gun, a personal shield, reflex boosters, a crew-automation suite, a command interface that shortens the stance-switch timer, and (still on the drawing board) self-repair and morale/fury. Every one of them is the *same* component with different defaults: **pick what it improves, then pick by how much.** One forced choice, one capability slider.

The shape is a **two-level forced choice + one or two sliders.** First you pick a *kind* (Augmentation / Advanced Training / Systems — the three "6.x" doors), which narrows the list; then you pick a *template* (which single sim number the part writes); then you set the **capability** slider (how much better) and — on five of the nine templates — a **separate declared-mass** slider (the "price" you type in yourself). The whole point of the door, per its own prose, is that on those five templates the price is a free dial disconnected from the capability, so you can take maximum capability for a kilogram. Two templates (`ground-training-cadre`, `sealed-systems`) already price the capability *into* the mass; a checkbox lets you preview that fix on the rest.

### A.3 Toggles / checkboxes / presets / secondary choices

| Control | id | Effect when active |
|---|---|---|
| "Price the capability into the mass…" checkbox | `fix` | Turns the free declared-mass dial into a capability-driven **floor** (the proposed fix, "slice E1"). For `caliber`: `mass = declared * Math.max(0.3, 1 + (capv - E.cdef)*2.0)`. For the other unpriced (`carry`,`dodge`,`shield`,`crew`): `mass = Math.max(declared, capv*(E.mdef/E.cdef))` — a per-template floor so every shipped design stays byte-identical. Changes markers (`k_a1` from `dead`/"costs NOTHING" to `set`), the ladder test to "passes", and the help/verdict prose. No effect on already-priced templates. |

## D. NOTES / DISCREPANCIES

- **Two templates are engine-pending (no sim variable exists yet):**
  - **`fieldrep` (Field repair / self-repair)** — `priced:true`, mass `45*(1+rate*2.8)`, but **BLOCKED** on the parked *degraded-condition / per-component-damage model*. A Pulsar unit is "whole-or-dead," so there is **no damaged state** for a repair rate to act on. It is the Enhancers half of hole **H2**. `m_4` shows " blocked"; `v_a3` reads "BLOCKED: no damaged state to act on (whole-or-dead)".
  - **`fury` (Steadiness / fury)** — `priced:true`, mass `40*(1+steadiness*1.5)`, but **PROPOSED**: the engine has **no morale field** (grep of GroundCombat for morale/fury/suppress returns nothing). It is the SPEC for what the engine must add (per-unit morale state + rout threshold + charge-surge + fearless/berserk flag). Waits on the same whole-or-dead ruling as self-repair. `v_a3` reads "PROPOSED: no morale state to set yet".
- **`iface` variable name is `SwitchableAfter`** — the timestamp a fleet/formation may next change doctrine/stance. This is the one live re-task timer; both seats drive the same call (AI ground brain calls `TrySetStance`, player calls the same). The doc explicitly retracts an earlier "reaction/latency" framing: "the engine has no variable for [that]; the real variable is the switch cooldown."
- **Default-state discrepancy in the HTML itself:** the `caliber` chip carries `aria-pressed="true"` in markup, but the script initializes `let job='carry', kind='bio'` and re-stamps `aria-pressed` on load (lines 758–761), so the panel actually **opens on Augmentation → power armour (`carry`)**, not ship cadre. The visible default is `carry`.
- **The door's core defect (its whole thesis):** on five of nine templates `Mass` is a *separate free dial* from the capability (`Mass = PropertyValue('CarryMass'/'Cadre Mass'/'Automation Mass')`), so you can set capability to max and mass to min for free. The `fix` checkbox previews the already-written cure (a capability-driven floor, byte-identical at stock). This is the panel's own honesty story — the `costs NOTHING` (`mk.dead`) marker fires exactly when `!E.priced && !fixed`.
- **`power-armor` is worse than free — a bootstrap:** `StrengthBonus` *adds* to the carry budget (`capacity += StrengthBonus*c`) while `CarryMass` spends from it (`used += g.Mass*c`) — two independent dials, so net contribution `StrengthBonus - CarryMass` is player-chosen and can be `+2,999` on a 1 kg part. The carry budget has **no ceiling**; the fix is `Math.Max(CarryMass, StrengthBonus*0.1)` (LEVERAGE = 0.1, the ground-weapons' `AttackCarryFactor`).
- **Retracted homing (contradiction with a naive reading):** an earlier pass proposed "Threshold" and "Endurance" as new *Enhancer* doors, and used a Magnitude/Threshold/Endurance decomposition. The CORRECTION box (and the JS comment at lines 490–493) states the LOCKED decomposition is **Augmentation (bio) / Advanced Training (train) / Systems (sys)**; "Magnitude" is a **shared dial in 6.0, not a door**; Threshold + damage-control/redundancy are **Defense > Hardening 5.3**, not this door. Only self-repair (fieldrep, in Systems) is genuinely this door's unbuilt piece.
- **The four ground augments (`power-armor`, `shield-generator`, `ward-projector`, `reflex-booster`) are one attribute, four presets** — all carry the same five dials (`CarryMass`, `StrengthBonus 0..1000`, `EvasionBonus 0..1`, `ToughnessBonus 0..2`, `Shield`, `Regen`), each leaving the ones it doesn't use at zero. The designer collapses them to one component + one slider per axis. `GroundUnitAssembly` correctly stacks shields/evasion (ADD) but takes best-only for training/sealing (`if (t.TrainingMultiplier > bestTraining)`).
- **Two templates already price correctly and even flag their own coefficients:** `ground-training-cadre` ("Training is EARNED… FLAGGED balance values") and `sealed-systems` ("Sealing fraction + cost curve are FLAGGED balance values"). These are the reference implementations the fix transcribes.
