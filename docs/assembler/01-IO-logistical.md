# 01-IO-LOGISTICAL — Logistical, re-derived — thirteen boxes, two attributes, and the one cargo that has no consumer
> Source: `docs/Actual HTMLs Of designers/logisticalderived.html` · Component-designer door · Census (Phase 1 draft, unverified)

## What this door builds
This designer builds every **logistical component** in the game — cargo holds, warehouses, fuel tanks, ordnance racks, magazines, troop bays, passenger cabins, cryo bays, and spaceports/shuttlebays (thirteen shipped templates). The finding: strip away the labels and the simulation only ever receives **two things** — **a store** (`CargoStorageAtb(storeTypeID, maxVolume)`: a cargo-type string plus a volume) and **a mover** (`CargoTransferAtb(rate, range)`: how fast cargo crosses and from how far).

So the door is **one forced choice with two answers plus "both" (hold / move / both), a second forced choice for *what* it holds (the cargo type string), and two sliders (how much · and if it moves, rate ↔ range)**. Think of it like a shipboard storeroom: the only real questions are "what goes in this box, and how big is the box" — a magazine is a store of ammo, a fuel tank is a store of fuel, a troop bay is a store of troops. The cargo-type string is the entire difference between nine of the thirteen templates, because it decides **which consumer in the engine can read the contents**.

### A.3 Toggles / checkboxes / presets / secondary choices
| Control | id | Effect when active |
|---|---|---|
| "Apply the proposed fixes" (checkbox) | `fix` | Switches the panel from "what the game does today" to "what this door proposes." Changes three things at once: (1) **flat** rate × range — `k=Math.pow(3,(rvr-5)/4)`, `rate=0.001*(size*0.5)*k`, `range=1.5*(size*0.5)/k` (L2); (2) storage stops subtracting the rate — `held = asked - sizeEff` (L3); (3) troop-bay capacity costs mass (`mass = 5000*(asked/T.def)`) and cryo colonists gain a 30-day thaw cost / colonists gain an additive unload path. **Nothing here is built** — it is the proposal side-by-side with the shipped arithmetic. |
| Per-chip auto-load of the shipped design (implicit preset) | `STOCK` object | Each answer chip resets `d1`/`d2` to its **real shipped part** on click, so the panel opens reproducing the game rather than a guess (`for(const [kk,v] of Object.entries(STOCK[k]||{})) $(kk).value=v;`). |

## D. NOTES / DISCREPANCIES
- **Colonists (`typ='people'`) — the headline engine-pending output.** The compartment (volume, mass, crew, cost) is shipped and correct, but **nothing consumes colonists**: `m_4` reads "🔴 NOTHING", marked "NOTHING reads it". Waits on an additive population path — today "every write to colony population is a MULTIPLY (`newPop = value × (1 + growth + migration)`), `UpdatePopulation` is a SET, no `pop + n` anywhere," so zero is an absorbing state and `CreateColonyOrder` founds colonies at population 0. Proposed slices C1–C4 (`ColonistPacket : ICargoable`, the draft, the thaw, founding-not-free) are **explicitly not built**.
- **Strike/berth (`typ='strike'`) — engine-pending launch.** A docked craft is `ICargoable`, so `strikecraft-bay` *stores* one today (no ctor overload, no save-load L13 risk), but the **launch verb has no game caller**: `ParasiteLauncherReady` is "an event the engine defines and never fires," and `DockTools` "has no game caller." Marked ENGINE-PENDING.
- **Negative-storage bug (ordnance / `both`).** `Total Cargo Stored = Rack Size − Size Efficiency − Cargo Transfer Rate` subtracts a *rate* (units/sec) from a *volume* (m³). At template defaults (50,000 rack, 50,000 rate) it is **−500 m³**, and `CargoStorageAtb` has **no floor at zero** — installing it *subtracts* from the ship's ordnance store. The panel lets you reproduce it: Ordnance + Both, unticked, drag the rate up.
- **`LogiBaseAtb` — the only completely dead attribute in eight doors.** Real class, real template (`logistics-office`), real dial (`Logistic Capacity` 5–100), real shipped design, and **zero readers outside its own file**. Not surfaced as a settable output in the builder (it has no chip); flagged in prose as "a dial that looks live." Awaits a developer ruling: wire as the colony logistics-route cap, or delete.
- **`spaceport` defined twice (data defect, not a dial).** Same `UniqueID` in `installations.json` (loads first) and `storage.json` (loads second) — the mod loader **merges property-by-property**, so `storage.json` wins and the store is eaten: "every start's spaceport stores nothing." Invisible to `BaseModIntegrityTests` because a merge is not a skip. Seven `UniqueID` collisions found across 300 ids.
- **Constant-mass leaks make dials free.** `troop-bay` `Mass = 5000` constant (capacity + carry-class both free); a general cargo hold masses `Size Efficiency × 1.0` = **1% of what it holds** (1,000 m³ → 10 kg), so a ship's mass budget cannot constrain cargo. The "make the field kgs no tonnes" ruling restores ×100 (`Cargo Hold 5t` masses 5,000 kg).
- **`fuel-cargo-hold`** asks for **65 billion crew** (`CrewReq = PropertyValue('Tank Volume')`) — unbuildable; its honest twin `stainless-steel-fuel-tank` (crew 0, 4 shipped designs) is the model. **`space-port`** (hyphenated) has `CrewReq: "1000000"` hard-coded. Both flagged for deletion/fix, not re-tuning.
- **Verified-good templates to copy, not change:** `stainless-steel-fuel-tank` (mass from a 4 mm steel shell — a real square-cube law) and `ship-magazine` (`Mass = Ammo Capacity × 1.2`, the only honest cost chain and the only logistical template with non-zero `ResearchCost`).
- **Four parallel stores exist** that a proper Berth slice would unify: `CargoStorageDB` · `GroundBayAtb` · `EnergyStoreAtb` · `GroundMagazineAtb` — each re-inventing "a compartment that only accepts one kind."
- **`battery-storage` / `perishable-storage` / `strikecraft-bay`** are cargo-type strings with **no provider** (or, for food, newly wired) — reported as the usual silent `0` on a `CargoMath.GetFreeVolume` miss (a "cannot carry that" and "no room right now" read the same on the same gauge).
